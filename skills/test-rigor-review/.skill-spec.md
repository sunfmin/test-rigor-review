# skill-spec: test-rigor-review

| Field | Value |
|---|---|
| name | `test-rigor-review` |
| description | Review existing code for where property tests, fuzz tests, and mutation testing pay off, which existing ones are weak, and which refactors unblock them. Ranked report first, then write what the user picks. |
| target | dedicated repo `sunfmin/test-rigor-review` |
| visibility | public |
| needs | none bundled; uses whichever test tools the reviewed project has |

## should_fire

1. Review internal/billing and tell me where property-based tests would be worth adding.
2. 帮我看看这个包哪些地方该写属性测试、哪些该做模糊测试。
3. Our coverage is 90% but I don't trust it. Are these tests actually checking anything? Run mutation testing on the pricing package.
4. What in this codebase should we be fuzzing?
5. This order module is hard to test with generated inputs. What would I need to refactor to make property tests possible?

## decoys

1. Add a unit test for the new ParseDate function. (ordinary example test)
2. Build the refund feature test-first. (tdd)
3. Is this module too complex? Give me a design review. (complexity-review)
4. This test is flaky in CI, figure out why. (diagnosing-bugs)
5. Review my PR for Go conventions before I commit. (code-review / go-reviewer)
6. Write table-driven tests for this Go handler. (go-test-conventions)

## functional_test

Task: run the review on a small Go fixture package containing (a) an `Encode`/`Decode`
pair, (b) a `ParseHeader([]byte)` parser with manual index arithmetic, (c) a
`Refund` function that mixes a rule (refund total must not exceed paid) with a
database call and `time.Now()`, and (d) an existing property test whose generator is
narrowed and whose assertion checks only that no error occurred.

Success condition, all must hold:

1. Test candidates include a round-trip rule for (a) and a fuzz target for (b).
2. Refactors include extracting the refund rule from I/O and injecting time for (c),
   and name the invariant test it unlocks.
3. Weak existing tests flags (d) for narrowed inputs and for the weak assertion.
4. The report ends with three findings to do first.
5. No file in the fixture was modified.
